# ActionGate: independent evaluation runbook

Team: **DEFOZO SOFTWARE HOUSE**. Sole member: **Michał Kiełtyka**.

This runbook is a set of actions and expected checks, not a claim that all checks
have passed. Use the dated reports generated by this checkout for measured results.
The English dashboard and all example workflows use synthetic supplier data.
The demonstration sinks do not send messages to people or make payments.

## Prepare and start

Run these commands from the project root in PowerShell:

Prerequisites are Docker with Compose, PowerShell 7, Python, `uv`, `psst`,
Node.js 24 and npm on PATH. The verification wrapper runs the UI browser suite
on the host; prepare its pinned dependencies and Chromium before acceptance.

The secrets CLI is installed with `npm install -g psst-cli`; its
[upstream guide](https://github.com/Michaelliv/psst#installation) also documents
vault setup. On a new machine, run `psst init` from this project directory first.
Bootstrap then generates the application keys for your own installation.

```powershell
pwsh -File scripts/bootstrap.ps1 -Profile local
pwsh -File scripts/start.ps1 -Profile local
pwsh -File scripts/doctor.ps1
npm --prefix ui ci
Push-Location ui
npx playwright install chromium
Pop-Location
```

Shell equivalents are `scripts/bootstrap.sh`, `scripts/start.sh`, and
`scripts/doctor.sh`. UI dependencies use `npm --prefix ui ci`; on Linux prepare
the browser and its system libraries with
`(cd ui && npx playwright install --with-deps chromium)`.
Preparation needs Internet access to obtain pinned dependencies, images and
model artifacts. The prepared local profile must be
verified without paid provider credentials. The start helper reads scoped secrets
from psst; do not print them or copy them into chat, screenshots or the repository.

Open `http://127.0.0.1:8080`. If `ACTIONGATE_PORT` was explicitly changed, use that
port. Only the edge endpoint is published to loopback. Workers, database, OPA and
the controlled sinks remain on the Compose networks.

Enter the **Acme** workspace as **Admin**. This identity selector belongs to local
demo mode; it is not production sign-in. Check the **Overview** control states.
Unavailable dependencies must remain visible. `/health/live` proves only that a
process responds; `/health/ready` and an actual allowed workflow are separate checks.

The **Stream connected** label describes the event connection, not the protection
posture. Counts, operations, accounts and test results come from the server.
Refresh does not create or simulate events.

## 1. Complete a useful, legal workflow

1. In **Overview**, select **Legal supplier review**, then **Run workflow**.
2. CPU model inspection can take several minutes. Keep the request pending and
   inspect the recorded progress; do not repeatedly submit the same scenario.
3. Open **Investigate**, select the new workflow and inspect its operations.
4. Verify document access, the inherited classification, memory/report creation,
   released content and settlement. A decision of `allow` alone is insufficient:
   the execution must be `completed` and the expected resource must exist.
5. Open **Budgets** and inspect spent, reserved and available commitments. Local
   tokens and worker occupancy are distinct from a commercial API invoice.

## 2. Compare redaction with blocking

1. Open **Test Lab**, select **Personal data**, and run **Inspect input** while
   **Balanced** is active. Check the decision, matched rules and inspected output.
2. The profile selector reports the active server configuration. Activate
   **Strict** through Policies as described below, then repeat the same input.
   Personal data should be blocked. The test does not rely on a case ID.
3. In **Policies & feeds**, edit the actual active YAML. Change the configured
   `active_profile` or its PII action, inspect **Changes**, then **Validate**.
4. **Activate generation** remains disabled until that exact draft validates.
   Editing again invalidates its prior validation in the UI; the server validates
   again during publication. Confirm the read-back generation and repeat the input.
5. Restore the desired policy using a new activation. History must remain intact.

`Observe` is an advisory content profile for the synthetic test tenant. It does
not turn off identity, tenant, label or budget invariants. It is not full protection.

## 3. Prompt injection and independent hard controls

1. Run **Prompt injection** from Overview or edit **Indirect instruction** in
   Test Lab to use your own wording.
2. Read the semantic verdict, risk level, model identity and execution mode.
   `unknown` is not a benign verdict. A missing local model must not produce a pass.
3. Run **Cross-tenant access** and inspect its authorization rule and dispatch state.
   The foreign resource must not be read, even if a semantic detector is wrong.
4. The automated hard-control regression uses a deliberately incorrect benign
   semantic fixture. That fixture is a labeled contract test, not a live model result.
5. Try the **Quoted security text** sample. Legal discussion of an attack should
   be evaluated separately from an instruction to carry it out. Report false
   positives as failures to improve, not as extra protection.

## 4. Memory labels and public data

1. Run **Memory label inheritance**. Inspect the stored note, subsequent read and
   the shared root context in Investigate. Classification must not fall after a
   paraphrase, encoding, a delegated agent or a restart.
2. Inspect attempted public release from the confidential context. Check that the
   public sink has no forbidden effect, not just that an HTTP response is an error.
3. Separately run **Public projection**. Its trusted `supplier_public_view_v1`
   function copies approved fields from the supplier registry before confidential
   retrieval. It does not accept arbitrary model text as public content.
4. Confirm that the internal report still reaches its authorized same-tenant
   recipient without lowering the classification of the confidential workflow.

## 5. Exact approval and mutation attempts

1. Run **Exact payload approval**. Open its `waiting_approval` operation.
2. Inspect the exact content, logical recipient, payload hash and generation.
3. Switch the local demo role to **Approver**. **Approve exact payload** submits
   that inspected hash. The API also checks role, tenant and current policy.
4. Confirm the refreshed execution and controlled sink effect. Approval is neither
   declassification nor an increase in permitted recipients.
5. The automated approval tests modify the recipient/content, replay a grant and
   race policy changes. Check the resulting sink effect count and ledger entries.
   Reusing a previous idempotency key with changed arguments must produce a conflict.
6. Switch to **Analyst** and verify that approval controls are disabled and direct
   unauthorized API requests are rejected. Switch to **Globex** and confirm Acme's
   operation details are not accessible. The UI clears tenant-scoped query caches.

## 6. Budgets and worker termination

1. Run **Budget exhaustion**, then inspect the shared run-tree accounts.
2. Compare rejected admissions with the persisted reservation ledger. For every
   admitted reservation, applicable spent + reserved + requested must fit its limit.
3. Inspect unknown usage separately. A timeout or period rollover must not erase
   a potentially incurred commitment.
4. Review worker telemetry and the watchdog verification report. HTTP cancellation
   alone is not proof that inference stopped; a slot is reusable only after the
   worker's process termination has been confirmed.
5. When reducing a configured limit below existing commitments, an overcommitted
   account is an explicit state. Historical costs remain recorded and new work is denied.
6. Read **Pricing provenance** for the current catalog revision, verified control
   signature, review date and validity deadline. Each provider reservation retains
   its recorded price revision and policy generation. A newly published price does
   not reprice old usage; local worker tokens have no commercial API price.

## 7. Publish a feed rule and compare policies safely

1. In **Policies & feeds**, inspect the threat feed revision, signature evidence
   and expiry. Edit its JSON rules array.
2. Add a bounded marker rule, preserving existing rules:

```json
{
  "id": "jury.marker",
  "scope": "text",
  "selector": "text",
  "operator": "equals",
  "value": "JURY_SYNTHETIC_MARKER",
  "action": "block",
  "source": "urn:actiongate:jury-synthetic-fixture"
}
```

3. Choose **Publish signed revision**. Check the read-back revision and active
   generation. The publisher signs the data; the UI does not receive its private key.
4. Inspect that exact marker in Test Lab before and after publication. Remove the
   rule in a later signed revision and repeat. A rejected update must preserve the
   last valid feed. Feed data cannot grant permissions or increase budgets.
5. Edit a candidate policy and select **Compare decisions**. Inspect both the
   number of covered records and `insufficient_evidence`. A redacted audit fragment
   cannot reproduce a new DLP or semantic evaluation. Comparison must not execute
   business connectors or create sink effects.

## 8. Execute verification and export evidence

Run fixed interactive checks from **Test Lab**. The request starts a persisted test job and the
dashboard polls its status; a `running` job is not a pass. The control accepts a
suite name, never an arbitrary shell command. Interactive checks cover DLP,
typed calculation and selected real workflows. Their passing status does not
replace the full release acceptance command below.

The job records its policy generation, profile, reporting workspace and actual
workflow tenant. Interactive workflows execute in `synthetic_test_tenant`;
ad hoc playground inspections save an allowed report in the currently selected
workspace, shown on the playground badge. Strict expects the PII workflow to
block; Balanced expects redaction. Observe or disabled content controls produce
an explicit `advisory` assessment. Matching an advisory policy is not counted as
a protection pass. A generation change interrupts the job instead of combining
results from different policies.

The command-line acceptance entrypoint is:

```powershell
pwsh -File scripts/verify.ps1 -Suite all-local
```

`contract` uses controlled upstreams. `all-local` also requires real local models,
the database, policy engine, memory, MCP, two replicas and isolation checks. Missing
dependencies must fail with a nonzero exit. `live-provider` is separate and is
`not run` if no explicitly configured provider key is available. API cost fixtures
must be identified as simulations. Read execution mode and report timestamps.

For frontend contracts alone:

```powershell
npm --prefix ui ci
npm --prefix ui test
```

These Playwright checks use explicit API fixtures to test client behavior,
including exact-hash approval, disabled permissions, cache isolation, unsafe HTML,
unavailable state, policy revalidation, worker telemetry, reservation units and
mobile layout. They do not establish
that the backend controls passed their own acceptance tests.

To execute the supplied Python and TypeScript agent examples with two separate
workload identities, run `python scripts/verify_clients.py --base-url
http://127.0.0.1:8080`. This is a real inference-bearing check. Its
`artifacts/submission/client-examples.json` report correlates the original example
files with completed operations, audit and document connector receipts. Both
clients must succeed; a skipped language is not a pass.

`node scripts/verify_ui_workflow.cjs` drives the actual **Run interactive local
checks** button and verifies the resulting legal, PII, injection and foreign-tenant
workflows. Set `ACTIONGATE_BASE_URL` if the loopback port differs from 8080.
It requires the installed UI Playwright dependency and FFmpeg/FFprobe for recording.
The browser closes while the server job runs, then reopens the same persisted job
and its operations. The final MP4 visibly states the real duration of the omitted
wait, with both original clips and a detailed `ui-workflow.json` retained. Run this
check with a free model slot; it performs additional actual local inference.

Use **Audit JSONL** for security evidence, **Management CSV** for aggregates and
**Print report** for a printable current view. Exports must retain the session's
tenant/role restrictions and omit raw secrets, tokens and internal reasoning.
CSV cells must be neutralized against spreadsheet formulas.

## Synthetic policy comparison and reset

In **Policies & Feeds**, validate the draft YAML, then select **Compare synthetic
corpus**. The background job evaluates the separate 16-case calibration
corpus under the active and candidate configuration. It does not activate the
draft and does not dispatch business effects. New semantic observations are
charged to `synthetic_test_tenant`; changing the semantic runtime itself yields
`insufficient_evidence` until that runtime has been separately activated and
verified. A completed comparison is not a recall measurement. The 40 frozen
holdout cases remain exclusively in the acceptance suite.

The repeatable command-line counterpart is `python scripts/verify_policy_replay.py
--base-url http://127.0.0.1:8080`. It compares a query-local candidate whose balanced
profile reviews level 2 and blocks level 3, without changing the active generation.
It records the job, separate synthetic budget, completed guard observations and
absence of business operations in `artifacts/submission/policy-replay.json`.

An administrator in **Investigate** can create a signed audit checkpoint. Retain
the returned checkpoint and verification metadata alongside an exported JSONL
report. A checkpoint authenticates the persisted chain head; protect an external
copy if protection against database rollback is required.

In **Test Lab**, an administrator who selects **Synthetic test tenant** can reset
synthetic resources. This revokes existing runs and restores the demo objects.
It preserves audit history and financial obligations. The endpoint refuses an
ordinary tenant, so reset is not a way to delete another tenant's evidence.

## Interpretation and recovery

| Observation | Meaning and next check |
| --- | --- |
| `block` before dispatch | No upstream should have been invoked. Verify the receiver/call count. |
| `redact` | Check the actual released text and unchanged data classification. |
| `waiting_approval` | No business effect yet; inspect exact payload and current policy. |
| `output_blocked` | Upstream may have run and incurred cost; output was withheld. |
| `outcome_unknown` / `usage_unknown` | Retain commitments and reconcile the controlled connector; do not blindly retry. |
| Guard unavailable or malformed JSON | Required semantic inspection failed closed; recover the worker and rerun. |
| Feed expired | Publish a fresh signed snapshot; do not disable verification to make readiness green. |
| SSE reconnecting | Server query refresh still works; reconnect is not evidence of a protection failure or recovery. |

Do not reset shared volumes to make a failing test pass. Preserve the operation,
generation, audit and report IDs. A restart is useful only when the subsequent
read-back proves that grants, labels, commitments and audit history persisted.
